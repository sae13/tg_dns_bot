# پیشنهاد اصلاح مسیر استقرار روی کلودفلر ورکرز

## ۱. خلاصهٔ مسئله

هنگام آمادهسازی داستان نخست مشخص شد مقصد قطعی استقرار، کلودفلر ورکرز است؛ درحالیکه معماری فعلی یک پردازهٔ دائمی پایتون با دریافت طولانی تلگرام، قفل و محدودکنندهٔ نرخ درونحافظه و خاموشسازی کنترلشده را فرض میکند. این فرضها با اجرای درخواستمحور و توزیعشدهٔ کلودفلر ورکرز سازگار نیستند.

این یک سوءبرداشت از نیاز استقرار است، نه تغییر در هدف محصول. قابلیتهای ارسال، خواندن و راهنما همچنان معتبرند.

## ۲. تحلیل اثر

### اثر بر حماسهها

- ساختار سه حماسه حفظ میشود.
- حماسهٔ نخست باید پایهٔ اجرایی را از پردازهٔ پایتون به ورکر درخواستمحور تغییر دهد.
- حماسهٔ دوم باید خواندن عمومی را با پرسوجوی امن روی HTTPS و DNS-over-HTTPS پیاده کند، نه resolver سیستمی.
- حماسهٔ سوم باید کنترل قابلیتها را از متغیرها و رازهای محیط کلودفلر دریافت کند.

### اثر بر داستانها

- داستان ۱.۱ به راهاندازی پروژهٔ TypeScript، Wrangler، webhook تلگرام، رازها و bindings تغییر میکند.
- داستان ۱.۵ به استفاده از REST API کلودفلر با fetch تغییر میکند.
- داستان ۱.۷ مالکیت ترتیب و نرخ را به یک Durable Object هماهنگکننده منتقل میکند.
- داستان ۱.۸ retry و reconciliation را در بودجهٔ CPU و زمان درخواست ورکر بازتعریف میکند.
- داستان ۲.۱ از DNS-over-HTTPS استفاده میکند.
- داستانهای مربوط به خاموشسازی پردازه، long polling، asyncio، aiogram و محدودکنندهٔ درونحافظه حذف یا بازنویسی میشوند.

### تعارضهای اسناد

- PRD از نظر رفتار محصول عمدتاً معتبر است؛ فقط بخشهای عملیاتی که «محیط اجرای سرور» را القا میکنند باید به «رازهای محیط استقرار» تعمیم یابند.
- ستون فقرات معماری در الگوی اجرا، پشته، قفل، نرخ، lifecycle و استقرار تعارض بنیادی دارد و باید اصلاح شود.
- سند حماسهها و مشخصات داستان ۱.۱ باید اصلاح شوند.
- پروندهٔ وضعیت اسپرینت پس از اصلاح عنوان یا شمارهٔ داستانها دوباره تولید میشود.

### اثر فنی

معماری پیشنهادی:

- زبان و زمان اجرا: TypeScript روی Cloudflare Workers.
- ورودی: webhook تلگرام روی یک مسیر تصادفی/محافظتشده؛ اعتبارسنجی هدر secret token تلگرام.
- خروجی تلگرام: فراخوانی مستقیم Bot API با fetch.
- نوشتن DNS: فراخوانی REST API کلودفلر با fetch و API Token محدود.
- خواندن DNS: DNS-over-HTTPS با پاسخ JSON یا wireformat معتبر.
- هماهنگی: یک Durable Object برای پذیرش اتمی سهمیهٔ فرستنده و صندوق، صف ترتیبی هر صندوق و state گذرای reconciliation.
- زمانبندی: Cron Trigger فقط برای reconciliation و پاکسازی دورهای قابل اثبات؛ صحت پیام جاری به اجرای cron وابسته نیست.
- تنظیمات غیرمحرمانه: vars و bindings در wrangler؛ رازها با secret store.
- آزمون: Vitest و محیط تست Workers؛ fetchهای تلگرام، Cloudflare API و DoH کاملاً mock شوند.
- استقرار: Wrangler و webhook registration پس از deploy؛ long polling و container حذف میشوند.

## ۳. مسیر پیشنهادی

گزینهٔ منتخب: اصلاح مستقیم برنامه با بازنگری معماری.

دلیل:

- هنوز هیچ کد محصولی ساخته نشده و rollback لازم نیست.
- هدف MVP و سه سفر کاربر تغییر نمیکنند.
- TypeScript مسیر بومیتر، کمریسکتر و قابل نگهداریتری برای Workers نسبت به Python/Pyodide است.
- Durable Object سادهترین راه برای حفظ ناوردای ترتیب و محدودسازی نرخ در اجرای توزیعشده است؛ پیچیدگی آن برای این محصول کوچک از طراحی هماهنگی چندموجودیتی کمتر است.

برآورد اثر: متوسط.

ریسک: متوسط، عمدتاً در قرارداد Durable Object، idempotency تغییرات DNS و webhook امنیتی.

## ۴. تغییرهای دقیق پیشنهادی

### معماری

قدیم:

- Python و aiogram
- long polling
- یک پردازه یا کانتینر
- قفل و نرخ در حافظه
- resolver سیستمی
- shutdown و drain پردازه

جدید:

- TypeScript و Cloudflare Workers
- webhook تلگرام
- Worker stateless بههمراه Durable Object هماهنگکننده
- محدودسازی نرخ و ترتیب صندوق در Durable Object
- DNS-over-HTTPS
- deploy با Wrangler و ثبت webhook
- lifecycle درخواستمحور؛ بدون shutdown پردازه

### داستان ۱.۱

قدیم:

راهاندازی اسکلت پایتونی، تنظیمات نوعمند، بررسی دسترسی و شروع polling.

جدید:

راهاندازی پروژهٔ TypeScript با Wrangler، مسیر سلامت و webhook، bindings و secrets نوعمند، بررسی secret token تلگرام، composition بدون اثر جانبی و آزمون محلی Workers. ثبت webhook و بررسی دسترسی Cloudflare در فرمان استقرار جدا انجام میشود، نه startup هر isolate.

### داستان ۱.۷

قدیم:

صف و محدودسازی نرخ در حافظهٔ یک پردازه.

جدید:

یک Durable Object هماهنگکننده که پذیرش دوکلیدی، ترتیب FIFO هر صندوق و idempotency رویداد تلگرام را در تراکنش ذخیرهسازی خود اعمال میکند.

### داستان ۲.۱

قدیم:

پرسوجو با dnspython و resolver عمومی.

جدید:

پرسوجوی DNS-over-HTTPS با fetch، timeout، اعتبارسنجی پاسخ و نمایش همهٔ TXT RRها.

### پشته

- TypeScript
- Cloudflare Workers و Wrangler
- Durable Objects
- Vitest و ابزار تست Workers
- fetch استاندارد برای Telegram Bot API، Cloudflare REST API و DNS-over-HTTPS

## ۵. تحویل اجرا

ردهٔ تغییر: عمده در معماری، متوسط در backlog، بدون تغییر راهبرد محصول.

مسئولیتها:

- معمار: اصلاح ستون فقرات معماری و حذف تصمیمهای پردازهٔ پایتون.
- مالک محصول: تأیید حفظ رفتار عمومی، کمسرعت و بدون تاریخچه.
- عامل توسعه: اصلاح داستان ۱.۱، ساخت مشخصات تازه و سپس پیادهسازی TypeScript.
- عامل آزمون: پوشش webhook جعلی، Durable Object، retry و APIهای mock.

معیار موفقیت اصلاح مسیر:

- هیچ وابستگی به Python، aiogram، long polling یا container در برنامهٔ MVP باقی نماند.
- webhook فقط درخواست دارای secret token معتبر را بپذیرد.
- ترتیب ارسال یک صندوق و محدودیت نرخ در اجرای همزمان و توزیعشده حفظ شود.
- هیچ آزمون به Telegram، Cloudflare API یا DNS واقعی متصل نشود.
- deploy با Wrangler و ثبت webhook قابل تکرار باشد.
